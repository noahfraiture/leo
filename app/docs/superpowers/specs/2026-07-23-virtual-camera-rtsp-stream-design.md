# Virtual Camera RTSP Stream Design

Date: 2026-07-23

Issue: [#22](https://github.com/noahfraiture/leo/issues/22)

## Summary

The virtual Axis camera will expose a prepared H.264 MP4 fixture through a standard RTSP endpoint. The Rust `camera` process will continue to own camera state and the VAPIX-compatible HTTP API, while a supervised MediaMTX child process owns RTSP, RTP, RTCP, timing, looping, and multiple readers.

This increment proves one static looping feed. API-driven fixture switching, Synology simulator ingestion, real-system validation, and desktop rendering are separate follow-up issues.

## Goals

- Let the app, the Synology simulator, real Surveillance Station, and standard media tools consume the mock through the same RTSP boundary as a physical camera.
- Expose an Axis-compatible stream path at `/axis-media/media.amp`.
- Replay a deterministic repository fixture continuously without FFmpeg at runtime.
- Keep each virtual camera independently addressable so multiple camera processes can run concurrently.
- Support at least two simultaneous RTSP readers.
- Fail clearly when the fixture, MediaMTX executable, configuration, or RTSP listener is unavailable.
- Keep MediaMTX replaceable by exposing only standard RTSP to consumers.

## Non-Goals

- Rendering the stream in the Dioxus app.
- Consuming or recording RTSP in the Synology simulator.
- Switching fixtures in response to VAPIX commands.
- Dynamically decoding, cropping, overlaying, or encoding video.
- Audio, H.265, MJPEG, ONVIF discovery, RTSPS, or SRTP.
- UDP or multicast transport in the first increment.
- RTSP or VAPIX authentication. Authentication will be designed when credential handling is implemented end to end.
- Production-grade child restart or media recovery. This is deterministic test infrastructure.

## Decision

Use MediaMTX instead of a Rust RTSP server or GStreamer.

MediaMTX is a mature, dependency-free media router that supports RTSP servers, RTP over RTSP/TCP, RTCP, multiple readers, and continuous MP4 fallback playback. Version 1.18.2, currently available in the Nix package set, includes `alwaysAvailable` and `alwaysAvailableFile`.

The rejected alternatives are:

- `rtsp-rs`: its current server lacks RTP-over-RTSP/TCP, advertises UDP ports it does not bind, sends RTP from an unrelated ephemeral port, omits RTCP and authentication, and does not test media reception.
- A custom Rust server: this would make the project responsible for RTSP sessions, SDP, RTP packetization, RTCP, transport negotiation, timing, and client interoperability.
- GStreamer: it is appropriate when runtime media transforms or decoded AI frames are required, but its native runtime and packaging complexity are unnecessary for static H.264 replay.

## Architecture

```text
prepared H.264 MP4
        |
        v
MediaMTX child process
        |
        +--> rtsp://host:port/axis-media/media.amp
                 |
                 +--> standard media tools
                 +--> Synology simulator in #46
                 +--> desktop preview in #38

Rust camera process
|-- owns camera identity and state
|-- serves /health and /axis-cgi/*
|-- generates the MediaMTX runtime configuration
|-- starts MediaMTX before reporting ready
\-- terminates MediaMTX when the camera exits
```

One Rust process and one MediaMTX child represent one virtual camera. Running another camera requires distinct HTTP and RTSP addresses and starts another pair of processes. There is no centralized mock-camera registry.

## Public Interface

The initial CLI is:

```text
camera \
  --address 127.0.0.1:8001 \
  --rtsp-address 127.0.0.1:8554 \
  --video camera/fixtures/default.mp4
```

All three arguments are required. The HTTP address retains its current meaning. The RTSP address controls the MediaMTX listener. The video path identifies one prepared local MP4 file.

The public stream URL is:

```text
rtsp://127.0.0.1:8554/axis-media/media.amp
```

RTSP query parameters may be accepted and ignored so consumers can use an Axis-shaped URL. The stream is anonymous and uses RTP over RTSP/TCP only.

## Fixture Contract

The repository contains one small fixture that is generated by the project or otherwise has documented redistribution rights. It must not contain private student footage.

Prepared fixtures use:

- MP4 container
- one H.264 video track
- 1280x720 resolution
- 15 frames per second
- baseline profile, level 3.1
- YUV 4:2:0 pixel format
- no B-frames
- closed one-second GOPs
- no audio or other tracks

The project adds a `just prepare-camera-video INPUT OUTPUT` command. Its FFmpeg operation is equivalent to:

```sh
ffmpeg -i "$INPUT" -an \
  -vf "fps=15,scale=1280:720:force_original_aspect_ratio=decrease,pad=1280:720:(ow-iw)/2:(oh-ih)/2" \
  -c:v libx264 -preset slow -crf 28 -profile:v baseline -level:v 3.1 \
  -pix_fmt yuv420p -bf 0 -g 15 -keyint_min 15 -sc_threshold 0 -flags +cgop \
  -movflags +faststart "$OUTPUT"
```

FFmpeg is present in the development shell for fixture preparation and acceptance checks. It is not launched by the camera.

The camera validates that the path exists and is a regular file before starting MediaMTX. MediaMTX performs the container and codec validation. More detailed cross-fixture validation belongs to fixture switching in #45.

## MediaMTX Configuration

The camera writes a per-process temporary MediaMTX configuration containing only fixed project settings and safely quoted absolute paths.

The configuration:

- enables RTSP
- binds `rtspAddress` to the CLI value
- allows only TCP RTSP transport
- disables RTMP, HLS, WebRTC, SRT, playback, metrics, pprof, and the control API
- defines the path `axis-media/media.amp`
- enables `alwaysAvailable`
- sets `alwaysAvailableFile` to the canonical fixture path
- leaves reads anonymous
- emits logs to standard error or standard output inherited by the camera process

The control API is not needed for a static feed. It will be enabled on a loopback address only when #45 adds fixture switching.

## Startup And Shutdown

Startup order:

1. Parse CLI arguments.
2. Canonicalize and validate the fixture path.
3. Write the temporary MediaMTX configuration.
4. Start MediaMTX with kill-on-drop behavior.
5. Wait up to five seconds for the RTSP TCP listener to accept a connection.
6. Start the Axum HTTP listener and report the camera ready.

If MediaMTX exits before readiness, the camera returns an error containing the child exit status. If the readiness deadline expires, the child is terminated and startup fails.

While running, the camera waits for either the Axum server or MediaMTX to exit. An unexpected MediaMTX exit terminates the camera with an error rather than leaving an HTTP-only camera that appears usable.

On normal camera shutdown, the camera explicitly terminates and waits for the child. Kill-on-drop behavior is the fallback if the Rust process unwinds or exits early. The temporary configuration is deleted when its owner is dropped.

The camera does not restart MediaMTX. Process restart belongs to the caller or test harness.

## Error Model

Non-trivial process and configuration errors live in the relevant module's `error.rs` and derive `thiserror::Error`.

Startup errors distinguish:

- invalid fixture path
- temporary configuration creation failure
- MediaMTX executable not found
- MediaMTX spawn failure
- RTSP readiness timeout
- MediaMTX early exit
- HTTP or RTSP address conflict

MediaMTX logs remain visible for protocol and fixture details. Errors must not claim the camera is ready when only its HTTP endpoint is available.

## Validation

Automated checks cover:

- parsing `--address`, `--rtsp-address`, and `--video`
- rejecting a missing or non-file fixture
- generating the intended RTSP-only MediaMTX configuration
- propagating a missing MediaMTX executable or occupied RTSP address
- terminating the child when the camera exits

An integration check in the Nix development environment:

1. Prepares or uses the committed fixture.
2. Starts the camera on unused local HTTP and RTSP ports.
3. Opens the Axis-compatible RTSP URL with FFprobe or FFmpeg over TCP.
4. Reads for longer than two fixture durations to prove looping.
5. Runs two readers concurrently.
6. Stops the camera and verifies that both listeners close.

Real Surveillance Station compatibility is not a normal CI gate. It is tracked by #44 and must prove registration, recording across two fixture loops, and recovery after a camera restart on the selected hardware.
